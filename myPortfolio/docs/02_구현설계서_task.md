# 02. 구현 설계서 및 태스크

## 1. 구현 목표

GitHub Pages에서 바로 배포 가능한 정적 멀티페이지 포트폴리오 사이트를 구축한다.  
공통 레이아웃과 공통 스크립트를 사용해 페이지별 중복을 줄이고, 실제 운영 시에는 데이터 파일만 수정해 전체 콘텐츠를 교체할 수 있도록 설계한다.

## 2. 구현 태스크 목록

### Task 1. 기본 파일 구조 설계

- 루트에 `index.html`, `404.html`, `README.md` 배치
- 페이지별 폴더 `projects/`, `services/`, `about/`, `contact/` 생성
- 각 폴더에 `index.html` 생성
- 공통 리소스 폴더 `assets/css`, `assets/js` 생성

### Task 2. 공통 레이아웃 구성

- 상단 헤더, 브랜드 영역, 네비게이션, 언어 전환 UI 설계
- 페이지별 공통 푸터 구성
- 각 페이지는 `#app` 하나만 두고 공통 스크립트가 내용을 렌더링하도록 구성

### Task 3. 시각 스타일 설계

- 정적 템플릿 느낌을 줄이기 위한 배경 레이어, 블러 오브젝트, 카드형 레이아웃 적용
- 큰 타이포 중심의 히어로 섹션 설계
- 실험적이지만 과하지 않은 인터랙션으로 스크롤 reveal 애니메이션 적용
- 모바일 반응형 레이아웃 대응

### Task 4. 데이터 구조 설계

- `site-data.js`에 사이트 전체 콘텐츠를 객체 형태로 저장
- 공통 정보:
  - 브랜드명
  - 역할
  - 이메일
  - GitHub 링크
  - 위치
- 페이지별 정보:
  - 홈 소개
  - 서비스 목록
  - 프로젝트 목록
  - 소개/작업 방식
  - 문의 안내
- 각 텍스트는 `ko`, `en` 키를 가진 다국어 구조로 관리

### Task 5. 공통 렌더러 구현

- 현재 페이지를 `body[data-page]` 값으로 판별
- 루트/하위 페이지 여부를 `body[data-depth]` 값으로 판별
- 페이지별 렌더링 함수를 분리
  - `renderHome`
  - `renderProjects`
  - `renderServices`
  - `renderAbout`
  - `renderContact`
  - `renderNotFound`
- 공통 헤더/푸터 렌더링 함수 구현

### Task 6. 언어 전환 기능 구현

- `localStorage`에 선택한 언어 저장
- 초기 진입 시 저장된 언어 또는 `?lang=` 쿼리 파라미터 우선 적용
- 언어 토글 클릭 시 전체 페이지 재렌더링

### Task 7. GitHub Pages 대응

- 상대 경로 기반 링크 구성
- 루트 페이지와 하위 페이지에서 에셋 경로가 모두 동작하도록 설계
- `404.html` 제공
- Open Graph 이미지와 favicon 포함

## 3. 상세 설계

### 3.1 페이지 설계

#### 홈

- 서비스 제안 중심 히어로 메시지
- 보조 CTA와 프로젝트 이동 버튼
- 현재 작업 방향을 보여주는 패널
- 핵심 강점 3개 카드

#### 프로젝트

- 결과 중심의 프로젝트 카드 목록
- 역할, 설명, 결과, 사용 기술 표시

#### 서비스

- 제공 가능한 서비스 패키지 설명
- 항목별 메타 정보와 기술/형태 태그 제공

#### 소개

- 작업 방식과 협업 기준 설명
- 작업 흐름 타임라인
- 다루는 기술/영역 태그

#### 문의

- 이메일, GitHub 링크 제공
- 문의 전에 함께 전달하면 좋은 정보 안내

### 3.2 자산 설계

- `assets/css/styles.css`
  - 전체 레이아웃
  - 컬러 변수
  - 카드/패널 스타일
  - 반응형 규칙
  - 애니메이션 스타일
- `assets/js/site-data.js`
  - 텍스트와 반복 목록 데이터 보관
- `assets/js/app.js`
  - 렌더링 로직
  - 언어 처리
  - reveal 인터랙션

## 4. 구현 시 의사결정 내역

- 프레임워크 대신 순수 정적 구조를 선택해 GitHub Pages 배포 단순성을 확보했다.
- 빌드 없는 다국어 처리를 위해 라이브러리 없이 객체 기반 번역 구조를 사용했다.
- 콘텐츠가 없더라도 완성형 UI를 먼저 만들 수 있도록 더미 데이터 기반 렌더링 방식을 선택했다.
- 네비게이션과 콘텐츠 출력을 공통 스크립트로 몰아 페이지별 중복 마크업을 줄였다.
- 문의 기능은 폼이 아닌 메일/링크 방식으로 제한해 정적 배포 제약을 따랐다.

## 5. 검증 항목

- 각 페이지 HTML이 정상 로드되는지 확인
- JS 문법 오류가 없는지 `node --check`로 확인
- 언어 전환 후 전체 페이지가 재렌더링되는지 확인
- 상대 경로 링크가 루트/하위 페이지에서 모두 동작하는지 확인
- 모바일 화면에서 컬럼 레이아웃이 1열로 전환되는지 확인
